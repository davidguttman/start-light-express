# Codebase Map: Start Light Express

This document provides a comprehensive overview of the `start-light-express` application, from its high-level architecture to the detailed flow of data. It is intended to help a new developer get up to speed quickly.

---

## 1. High-Level Architecture Overview

### Overall Architecture
The application is a **Single Page Application (SPA) with a monolithic backend API**.

*   The **Backend** is a standard Express.js server that exposes a RESTful API and handles authentication.
*   The **Frontend** is a client-side application built with modern JavaScript but without a major framework like React or Vue. It uses lightweight libraries for routing, templating, and DOM updates.
*   In **development**, the backend server (`server.js`) acts as a proxy, forwarding UI-related requests to a separate Vite development server. This provides a seamless developer experience with hot-reloading for the frontend and auto-restarting for the backend, all accessible through a single port.
*   In **production**, the Express server is expected to run as an API-only service, with the static frontend assets served separately, likely from a CDN.

### Technology Stacks
*   **Backend**:
    *   **Framework**: Express.js
    *   **Database**: MongoDB with Mongoose (ORM)
    *   **Authentication**: `authentic-service` for token validation.
    *   **Configuration**: `dotenv` for environment variables.
    *   **Testing**: `tape` (test runner), `supertest` (HTTP assertions).
*   **Frontend**:
    *   **Build/Dev Tool**: Vite
    *   **Routing**: `http-hash` (client-side hash-based routing).
    *   **Templating/DOM**: `nanohtml` & `nanomorph` for creating and updating HTML elements efficiently.
    *   **Authentication**: `authentic-ui` for rendering login/signup forms and handling user sessions.
    *   **State Management**: A custom, lightweight event-emitter pattern using `wildemitter`.

### Core Architectural Patterns
This codebase makes excellent use of several key patterns to manage complexity and different environments.

*   **Environment-Specific Module Loading (Dependency Swapping)**: This is the most critical pattern to understand. The application dynamically loads different modules based on the `NODE_ENV` environment variable. This allows for mocking core services during testing without littering the production code with conditional logic.
    *   **Database**: `lib/mongo/index.js` checks `NODE_ENV`. If `test`, it loads `lib/mongo/mock-mongo.js`, which spins up an in-memory MongoDB server. Otherwise, it loads `lib/mongo/mongo.js`, which connects to a real MongoDB instance.
    *   **Authentication**: `middleware/index.js` checks `NODE_ENV`. If `test`, it loads `middleware/auth-test.js`, which uses a simple, predictable static token for authentication. Otherwise, it loads `middleware/auth.js`, which integrates with the `authentic-service` for real token validation.

*   **Asynchronous Error Handling Wrapper**: The `lib/auto-catch.js` utility is a higher-order function that wraps async Express route handlers. It provides a `try/catch` block, ensuring that any exceptions thrown in the async logic are passed to Express's error-handling middleware (`next(err)`). This keeps the route definitions in `api/*.js` clean and concise.

*   **Centralized API Client**: On the frontend, `client/api.js` provides a single `apiCall` function. This function abstracts the `fetch` API, automatically attaches the `Authorization` header to requests, and provides centralized handling for `401 Unauthorized` responses by redirecting the user to the login page. This prevents an invalid token from breaking individual components.

*   **Development Proxy**: The development environment (`npm run dev`) uses a proxy pattern defined in `lib/client-setup.js`. The main Express server (on `localhost:3000`) starts up and then programmatically starts the Vite dev server on a different port (e.g., `5173`). An Express middleware is registered to proxy any request that *is not* for the API (`/api/*`) or health check (`/health`) over to the Vite server. This is visualized in section 5.

## 2. Detailed Directory & File Analysis

This section provides a hierarchical breakdown of the project.

-   `.specstory/`
    -   `.gitignore`: **WHAT**: Ignores files generated by the SpecStory tool.
-   `api/` - **(Subsystem: Backend API Routes)**: This directory contains all the Express router definitions for the backend API.
    -   `auth-test.js`: **WHAT**: Defines test-only API endpoints (`/authTest`, `/errorTest`) used for frontend diagnostics.
    -   `widgets.js`: **WHAT**: Defines the primary CRUD (Create, Read, Update, Delete) API endpoints for the `Widget` resource.
-   `client/` - **(Subsystem: Frontend Single Page Application)**: Contains all the source code for the client-side application.
    -   `style/`
        -   `index.js`: **WHAT**: Injects all application CSS into the DOM using the `insert-css` library.
    -   `api.js`:
        -   **WHAT**: Provides a centralized function (`apiCall`) for making frontend API requests.
        -   **WHY**: This file exists to abstract away the details of `fetch` and to centralize logic common to all API calls, such as adding authentication headers and handling authorization errors (e.g., 401 Unauthorized, which triggers a redirect to the login page).
        -   **Key Functions**:
            -   `apiCall(url, options)`: Wraps the `fetch` API. It reads the current authentication token from `auth.js` and adds it to the request headers. It also includes robust error handling for HTTP statuses, converting them into meaningful JavaScript `Error` objects and handling session expiry specifically.
    -   `auth.js`:
        -   **WHAT**: Manages all frontend authentication logic, state, and UI components.
        -   **WHY**: This is the central hub for user authentication on the client. It integrates with the `authentic-ui` library to render forms and manage tokens in `localStorage`, and it provides a clean interface for the rest of the app to access the user's authentication status. It also handles the `FORCE_AUTH_EMAIL` development bypass.
        -   **Key Functions**:
            -   `initAuthState()`: Initializes the `authState` object on application load by checking `localStorage` (via `aui.authToken()`) or the `__FORCE_AUTH_EMAIL__` global.
            -   `getAuthState()`: Returns the current authentication state (isLoggedIn, email, authToken).
            -   `handleLogout()`: Clears the auth token and redirects the user to the home page.
            -   `createLogin()`, `createSignup()`, etc.: Functions that return the corresponding HTML elements generated by `authentic-ui` for use in the router.
    -   `main.js`:
        -   **WHAT**: The main entry point for the client-side application.
        -   **WHY**: This file orchestrates the entire frontend. It sets up the router, defines the application's routes, and manages the main render loop. It is responsible for rendering the correct "page" based on the URL hash and the user's authentication state.
        -   **Key Sections/Functions**:
            -   **Router Setup**: An instance of `http-hash` is created, and routes like `/`, `/widgets`, and `/login` are mapped to handler functions (UI components).
            -   `navigate()`: The core render function. It gets the current URL hash, applies route guarding logic from `route-guard.js`, retrieves the appropriate page component from the router, and renders the complete application shell using `nanohtml`. It uses `nanomorph` to efficiently update the DOM on subsequent navigations, preventing full-page reloads.
            -   **Event Listener**: Attaches the `navigate` function to the `hashchange` browser event.
    -   `navigation.js`: **WHAT**: Creates the main top navigation bar component, which reactively shows/hides links based on the user's login status.
    -   `route-guard.js`: **WHAT**: Implements logic to protect routes. It defines which routes are public vs. protected and redirects users if they try to access a page they are not authorized for.
    -   `settings.js`: **WHAT**: The UI component for the "/settings" page. Includes diagnostic buttons to test server health and authentication.
    -   `state.js`: **WHAT**: A lightweight, generic state management utility built on `wildemitter`, allowing components to have reactive state.
    -   `user-info.js`: **WHAT**: A simple UI component that displays the logged-in user's email address.
    -   `welcome.js`: **WHAT**: The UI component for the home page (`/`).
    -   `widgets.js`: **WHAT**: The UI component for the "/widgets" page. It handles fetching, displaying, creating, and deleting widgets.
-   `config/`
    -   `index.js`:
        -   **WHAT**: Loads and exports all application configuration.
        -   **WHY**: This file centralizes configuration management. It loads variables from `.env` files, provides sensible defaults, and initializes services like the logger (`productionize`) and authentication (`authentic-service`) that depend on this configuration.
        -   **Key Sections**:
            -   **Defaults**: Defines default values for all config variables.
            -   **Environment Merge**: Overwrites defaults with values from `process.env`.
            -   **Service Initialization**: Creates and exports instances of `logger` and `auth`.
-   `lib/` - **(Subsystem: Core Backend Libraries)**
    -   `mongo/` - **(Subsystem: Database Abstraction)**: This module cleverly abstracts the database connection to support both real and in-memory databases for production and testing.
        -   `index.js`:
            -   **WHAT**: The public interface for the database connection.
            -   **WHY**: This is a critical architectural file. It uses a dynamic `import()` to conditionally load either the real or mock MongoDB module based on `NODE_ENV`. Any part of the application that needs a database connection just imports this file, and the correct implementation is provided automatically.
            -   **Key Logic**:
                -   `if (process.env.NODE_ENV === 'test') { await import('./mock-mongo.js') }`
                -   `else { await import('./mongo.js') }`
        -   `mock-mongo.js`: **WHAT**: Connects to an in-memory MongoDB server (`mongodb-memory-server`) for testing. Includes a `cleanup` method to shut down the server.
        -   `mongo.js`: **WHAT**: Connects to a real MongoDB instance using the connection string from the configuration.
    -   `auto-catch.js`: **WHAT**: A higher-order function to wrap async Express route handlers and automatically catch errors.
    -   `client-setup.js`:
        -   **WHAT**: Manages the setup of the frontend development server and proxy.
        -   **WHY**: This file encapsulates the complex logic required for the development proxy pattern. It keeps `server.js` clean by handling the different setup steps required for development, production, and test environments.
        -   **Key Functions**:
            -   `setupDevServer(app)`: The main function. In development, it programmatically starts an instance of the Vite dev server and returns a proxy middleware for the Express app to use. In production/test, it does nothing.
-   `middleware/` - **(Subsystem: Backend Middleware)**
    -   `auth-test.js`: **WHAT**: A mock authentication middleware for the `test` environment. It authenticates any request with the static token `Bearer test-token`.
    -   `auth.js`: **WHAT**: The production authentication middleware. It uses `authentic-service` to validate JWTs and checks if the user's email is in the configured `WHITELIST`. It also handles the `FORCE_AUTH_EMAIL` developer bypass.
    -   `index.js`:
        -   **WHAT**: The public interface for the authentication middleware.
        -   **WHY**: Similar to `lib/mongo/index.js`, this file uses a dynamic `import()` to conditionally load either the real (`auth.js`) or mock (`auth-test.js`) middleware based on `NODE_ENV`. API routes in `api/*.js` just import and use this middleware, and they automatically get the correct version for the environment.
-   `models/`
    -   `widget.js`: **WHAT**: Defines the Mongoose schema and model for the "Widget" data structure.
-   `test/` - **(Subsystem: Automated Tests)**
    -   `api/`: Contains integration tests for the API endpoints.
        -   `health.test.js`: **WHAT**: Tests the `/health` endpoint.
        -   `widgets.test.js`: **WHAT**: Tests the CRUD operations for the `/api/widgets` endpoint.
    -   `helpers/`: Contains utility modules for testing.
        -   `cleanup.js`: **WHAT**: Exports a function to clean up test resources (specifically, shutting down the mock MongoDB server).
        -   `mock-auth.js`: **WHAT**: A simple mock authentication middleware (legacy, `middleware/auth-test.js` is what's actively used).
    -   `auth.test.js`: **WHAT**: Tests the behavior of the authentication middleware.
    -   `auto-catch.test.js`: **WHAT**: Unit tests for the `autoCatch` utility.
    -   `index.js`: **WHAT**: A custom test runner that finds and runs all `*.test.js` files. It is less common than using a framework like Jest but works effectively here.
    -   `mongo.test.js`: **WHAT**: Tests the health check functionality of the database connection.
    -   `run-tests.js`: **WHAT**: The entry script for `npm test`, which runs each test file in a separate child process to ensure isolation.
-   `.env.example`: **WHAT**: An example file showing all the required environment variables for the application.
-   `.gitignore`: **WHAT**: Specifies files and directories to be ignored by Git.
-   `index.html`: **WHAT**: The main HTML file for the single-page application. It contains a single script tag that loads the entire frontend.
-   `package.json`: **WHAT**: Defines project metadata, dependencies, and `npm` scripts.
-   `server.js`:
    -   **WHAT**: The main entry point for the backend Express server.
    -   **WHY**: This file is the heart of the backend. It ties everything together: it initializes the Express app, registers all middleware (JSON parsing, health checks, API routes, error handling), and starts the server. It also orchestrates the development proxy setup by calling `lib/client-setup.js`.
    -   **Key Sections**:
        -   **Middleware Registration**: `app.use()` calls for `express.json()`, the `/health` endpoint, API routers (`/api/widgets`, `/api/auth`), and the final error-handling middleware.
        -   **Server Startup**: The `if (import.meta.url === ...)` block ensures the server only starts when the file is run directly. It calls `setupDevServer`, registers the returned proxy middleware (if any), and then calls `app.listen()`.
-   `vite.config.mjs`:
    -   **WHAT**: The configuration file for Vite, the frontend build and development tool.
    -   **WHY**: This file is critical for the frontend to work correctly. It tells Vite where the source files are, how to build them, and how to run the development server. Most importantly, it uses the `define` option to inject server-side environment variables (`AUTHENTIC_SERVER`, `FORCE_AUTH_EMAIL`) into the client-side JavaScript bundle, making them available as global constants.

## 3. Key Data Flow Analysis

This section traces the primary user story of **"Creating a new widget"** from start to finish. This flow assumes the user is already logged in.

1.  **UI Interaction (`client/widgets.js`)**
    *   The user is on the `/#/widgets` page. They fill out the "Create New Widget" form (rendered by the `render` function) and click the "Create Widget" button.
    *   The form's `onsubmit` event triggers the `createWidget` function.

2.  **Frontend Logic (`client/widgets.js`)**
    *   The `createWidget` function reads the data from the form.
    *   It constructs a `widget` JavaScript object (e.g., `{ name: '...', quantity: '...'}`).

3.  **Centralized API Call (`client/widgets.js` → `client/api.js`)**
    *   `createWidget` calls `apiCall('/api/widgets', { method: 'POST', body: JSON.stringify(widget) })`.
    *   The `apiCall` function in `client/api.js` is executed. It gets the current auth token from `client/auth.js` and adds it to the request as an `Authorization: Bearer <token>` header.
    *   It uses `fetch` to send a `POST` request to the backend server.

4.  **Backend Request Handling (`server.js`)**
    *   The Express server receives the `POST /api/widgets` request.
    *   It passes the request through the middleware chain defined in `server.js`.

5.  **Authentication Middleware (`server.js` → `middleware/index.js` → `middleware/auth.js`)**
    *   The request hits the auth middleware imported from `middleware/index.js`. Since `NODE_ENV` is not `test`, this resolves to `middleware/auth.js`.
    *   The middleware function uses `config.auth` (the `authentic-service` instance) to parse and validate the bearer token from the header.
    *   It then checks if the user's email from the validated token is present in `config.whitelist`.
    *   If successful, it attaches the `user` object to the `req` and calls `next()`.

6.  **API Router (`api/widgets.js`)**
    *   The request is routed to the `widgetsRouter`.
    *   The `router.post('/', ...)` handler is matched. This handler is wrapped in `autoCatch`.

7.  **Controller & Database Interaction (`api/widgets.js` → `models/widget.js` → `lib/mongo/index.js`)**
    *   Inside the route handler, a new Mongoose model instance is created: `const widget = new Widget(req.body)`.
    *   `await widget.save()` is called. Mongoose validates the data against the schema in `models/widget.js` and saves the document to the MongoDB database via the connection managed by `lib/mongo/index.js`.
    *   The server sends a `201 Created` HTTP response containing the newly created widget data as JSON.

8.  **Frontend Response Handling (`client/widgets.js`)**
    *   The `fetch` promise in `client/api.js` resolves with the `201` response.
    *   The `await apiCall(...)` in `createWidget` completes. The function now has the response data.

9.  **UI Update and Re-render (`client/widgets.js` → `client/state.js`)**
    *   The `createWidget` function resets the form.
    *   It updates the component's state to show a temporary success message: `state.set({ success: 'Widget created...' })`.
    *   It calls `loadWidgets()` to refresh the list of widgets from the server. This initiates another `apiCall` (`GET /api/widgets`).
    *   When `loadWidgets()` completes, it updates the state with the new list: `state.set({ widgets: [...] })`.
    *   The call to `state.set()` triggers the `state.on('*', ...)` event listener defined in the component's main function.
    *   This listener re-runs the `render()` function to generate a new virtual DOM tree and then uses `morph(tree, newTree)` to efficiently update the actual DOM, displaying the new widget in the list and the success message.

## 4. Configuration and Environment Analysis

Configuration is managed via environment variables, loaded from a `.env` file in development using the `dotenv` package. The `config/index.js` file reads these variables, provides defaults, and exports them for use throughout the application.

Below is a cross-reference table of the key configuration variables.

| Config Key | Example Value / Source | Consumed In | Purpose |
| :--- | :--- | :--- | :--- |
| `NODE_ENV` | `development`, `test`, `production` (from `process.env`) | `lib/mongo/index.js`, `middleware/index.js`, `lib/client-setup.js` | **CRITICAL**: Controls which database and auth modules are loaded. Disables dev proxy in production/test. |
| `PORT` | `3000` (from `.env` or default) | `server.js` | The port the backend Express server listens on. |
| `MONGO_URI` | `mongodb://localhost:27017/` (from `.env`) | `lib/mongo/mongo.js` | The connection string for the real MongoDB database (used when `NODE_ENV` is not `test`). |
| `MONGO_DB_NAME` | `example` (from `.env`) | `lib/mongo/mongo.js` | The specific database name to use within the MongoDB instance. |
| `AUTHENTIC_SERVER` | `https://authentic.example.com` (from `.env`) | `config/index.js` (backend), `vite.config.mjs` → `client/auth.js` (frontend) | The URL of the `authentic-service` used for both backend token validation and frontend UI integration. |
| `WHITELIST` | `user1@example.com,user2@example.com` (from `.env`) | `middleware/auth.js` | A comma-separated list of email addresses that are authorized to use the application. |
| `FORCE_AUTH_EMAIL` | `dev@example.com` (from `.env`, dev only) | `middleware/auth.js` (backend), `vite.config.mjs` → `client/auth.js` (frontend) | **Development Only**: If set, completely bypasses real authentication. The backend treats all requests as authenticated by this email, and the frontend automatically logs in as this user. |
| `GOOGLE_PROJECT_ID` | `your-gcp-project` (from `.env`) | `config/index.js` | The Google Cloud Project ID for structured logging in production via `productionize`. |
| `GOOGLE_APPLICATION_CREDENTIALS` | `path/to/key.json` (from `.env`) | `config/index.js` | Path to the GCP service account credentials for structured logging in production. |

## 5. Architectural Visualization

The most complex and non-obvious interaction in this codebase is the **Development Server Proxy Setup**. When a developer runs `npm run dev`, two servers are started, but they work together to serve the application from a single port. This diagram explains how a request is routed.

```mermaid
sequenceDiagram
    actor Developer
    participant Browser
    participant Express Server (localhost:3000)
    participant Vite Dev Server (localhost:5173)

    Developer->>+Express Server (localhost:3000): Runs `npm run dev` which starts `server.js`
    Note over Express Server (localhost:3000),Vite Dev Server (localhost:5173): server.js calls setupDevServer()
    Express Server (localhost:3000)->>+Vite Dev Server (localhost:5173): Programmatically starts Vite server
    Vite Dev Server (localhost:5173)-->>-Express Server (localhost:3000): Vite is ready
    Note over Express Server (localhost:3000): Express registers a proxy middleware<br/>and starts listening on port 3000.

    Developer->>Browser: Opens http://localhost:3000/
    Browser->>+Express Server (localhost:3000): GET /
    Note over Express Server (localhost:3000): Proxy Middleware checks path.<br/>'/' is not '/api/*' or '/health'.
    Express Server (localhost:3000)->>+Vite Dev Server (localhost:5173): Proxies request: GET /
    Vite Dev Server (localhost:5173)-->>-Express Server (localhost:3000): Returns index.html
    Express Server (localhost:3000)-->>-Browser: Forwards index.html
    
    Note over Browser: Browser parses HTML, finds <script src="/client/main.js">

    Browser->>+Express Server (localhost:3000): GET /client/main.js
    Note over Express Server (localhost:3000): Proxy Middleware checks path.
    Express Server (localhost:3000)->>+Vite Dev Server (localhost:5173): Proxies request: GET /client/main.js
    Vite Dev Server (localhost:5173)-->>-Express Server (localhost:3000): Returns transpiled main.js
    Express Server (localhost:3000)-->>-Browser: Forwards main.js
    
    Note over Browser: App runs, user navigates, triggers API call.

    Browser->>+Express Server (localhost:3000): POST /api/widgets
    Note over Express Server (localhost:3000): Proxy Middleware checks path.<br/>Path starts with '/api/', so it's NOT proxied.
    Express Server (localhost:3000)->>Express Server (localhost:3000): Passes request to own API router
    Express Server (localhost:3000)-->>-Browser: Returns API JSON response (e.g., 201 Created)
```
